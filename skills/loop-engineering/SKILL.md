# Loop engineering

**先定义下一条证据，再开始等待。** 对每次实验写下：假设、最小可运行验证、预期新信号、检查点、总时限、失败时保留什么。不要把“进程还在”当成通过。

## 长任务先保存目标

先判断是否为长任务。判断不是长任务时，不要求为本原则专门建立持久记录；若执行中才发现是长任务，立即补记原始目标、已有进度和未完成项，再按本原则继续。初始即判断为长任务时，开始实质工作前按项目约定持久记录总体目标，不把当前实验或下一步当成整个任务。优先复用已有任务文档、issue 或跟踪系统；没有约定时建最小任务文件，并明确其路径/条目 ID。只依赖聊天摘要、临时计划或内存状态不够。

记录至少包含：用户目标、范围和逐项完成标准、授权与限制、已完成事项及证据、未完成事项、真实阻塞和下一步。不要写入凭据、认证状态或完整会话；必要的私有记录留在项目允许的非入库位置。

每个里程碑、范围变化、阻塞和交接时更新。上下文压缩/恢复后、改做其他任务前、宣告完成前重读并对照原目标；交接必须提供记录位置。未经用户确认不缩小范围，也不把子任务完成、离线检查或阶段工具当成总体完成。

遇到权限、审批或现场条件缺失，只暂停真正依赖它的步骤，继续其余已授权的实现与验证。把需人决定的条件及影响范围列清，不自行绕过；不能以“安全阻止执行”代替仍可完成的准备。暂停或预算耗尽时，更新记录并明确未完成项及继续条件。

## 缩短回路

1. 先跑秒级检查（语法、静态校验、假命令/小夹具）；复用已验证镜像跑单例，再跑从零构建。大下载和全量验收只作最后一层，不用于寻找可由小用例定位的故障。
2. 每次慢实验只变一个原因。输入和产物要钉住版本/路径；能拆开时，先保存耗时安装的不可变基底，再在克隆上调试易失败的配置/验收。选不会在配置失败后删掉基底的入口。
3. **等待前定检查点。** 以日志事件、端口、退出码、文件或 UI 状态为信号；能监听就监听，不用固定长 `sleep`。预计阶段本来要很久时记下预计时长和中途可观察信号，而不是盲目缩短它。
4. 若一次交互等待超过预计检查点（无估计时先用 90 秒），或连续两个检查点没有新证据：停止被动轮询，检查进程状态、最近日志、真正的 guest/服务状态和失败产物。没有可观察性时先加标记或小探针；不要只加大超时、重复同一命令。
5. 设**总时限**并区分结果：通过、明确失败、超时未知。GUI 用例以真实窗口或截图验收，不用 SSH/端口健康检查替代；打断时只清理自己创建的资源，保留快照/日志，不把另一平台的通过冒充本平台通过。

## 可复用的日志检查点

纯文本追加日志可用 `node scripts/wait-for-log.mjs <file> <pattern> <seconds>` 等一个状态（日志里已出现则立即返回 0，超时返回 124，参数/读取失败返回 2）。每次实验用独立日志，避免旧状态误命中。它只报告命中或超时，不回显日志正文，避免把凭据/临时控制口令印到输出。启动前先确定期望的下一行；看到超时先诊断，别原样重跑。

完成标准：每一层有可复述的证据与退出码；长任务对照持久记录逐项验收总体目标，记录已更新，未完成项和下一步明确；非长任务不要求为本原则专门建立持久记录；临时资源归还，未验证的层明确标记为未验证。局部通过不代表总体完成。
