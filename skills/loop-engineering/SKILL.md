# Loop engineering

**先定义下一条证据，再开始等待。** 对每次实验明确：假设、最小可运行验证、预期新信号、检查点、总时限、失败时保留什么。可在当前交互中说明，不必因此创建文件。不要把“进程还在”当成通过。

## 记录服从当前有效要求

本 Skill 提供反馈回路方法，不独立启用常驻策略。长任务持久记录的创建、更新和重读，遵循当前实际启用的 `repository/35-long-task-goals`，或用户/项目明确的任务记录要求；没有这些要求时，即使本 Skill 因长任务或等待被加载，也不自动创建持久文件、指定固定文件名或强制维护任务文档。反馈方法可直接用于当前交互，不需要任务文件。

当记录要求适用时，按其规定的时机、内容和位置执行，优先复用现有文档、issue 或跟踪条目；不要另叠一套保存流程。关闭 35 不禁止用户明确要求的任务文档或交接，也不取消项目独立规定的记录要求。凭据、认证和完整会话不入库。

总体目标/范围连续性和阻塞处理分别遵循当前有效的 `repository/36-goal-scope-continuity`、`repository/37-blocker-handling` 或用户/项目要求；本 Skill 不借加载恢复已关闭的策略。权限与真实性始终受当前强制安全边界约束。

## 缩短回路

1. 先跑秒级检查（语法、静态校验、假命令/小夹具）；复用已验证镜像跑单例，再跑从零构建。大下载和全量验收只作最后一层，不用于寻找可由小用例定位的故障。
2. 每次慢实验只变一个原因。输入和产物要钉住版本/路径；能拆开时，先保存耗时安装的不可变基底，再在克隆上调试易失败的配置/验收。选不会在配置失败后删掉基底的入口。
3. **等待前定检查点。** 以日志事件、端口、退出码、文件或 UI 状态为信号；能监听就监听，不用固定长 `sleep`。预计阶段本来要很久时记下预计时长和中途可观察信号，而不是盲目缩短它。
4. 若一次交互等待超过预计检查点（无估计时先用 90 秒），或连续两个检查点没有新证据：停止被动轮询，检查进程状态、最近日志、真正的 guest/服务状态和失败产物。没有可观察性时先加标记或小探针；不要只加大超时、重复同一命令。
5. 设**总时限**并区分结果：通过、明确失败、超时未知。GUI 用例以真实窗口或截图验收，不用 SSH/端口健康检查替代；打断时只清理自己创建的资源，保留快照/日志，不把另一平台的通过冒充本平台通过。

## 可复用的日志检查点

纯文本追加日志可用 `node scripts/wait-for-log.mjs <file> <pattern> <seconds>` 等一个状态（日志里已出现则立即返回 0，超时返回 124，参数/读取失败返回 2）。每次实验用独立日志，避免旧状态误命中。它只报告命中或超时，不回显日志正文，避免把凭据/临时控制口令印到输出。启动前先确定期望的下一行；看到超时先诊断，别原样重跑。

完成标准：每一层有可复述的证据与退出码；明确未完成项、下一步和未验证的层，归还临时资源，局部通过不代表总体完成。仅当当前记录策略或用户/项目明确要求适用时，才按该要求更新、重读持久记录并给出位置；没有记录要求时，不以缺少任务文件判定反馈验证未完成。
